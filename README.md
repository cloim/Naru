# Naru

Windows에서 컨테이너 엔진을 관리하는 로컬 웹앱입니다. External Engine의 기존 Docker 엔진 공유 연결과 Naru 독립 WSL 런타임을 지원합니다. External Engine 1.24.0 설치본의 REA 분석과 공식 소스를 참고했으며, UI와 제어 서버는 별도로 구현했습니다.

## 실행

Windows 11 또는 WSL 2를 사용할 수 있는 Windows와 Node.js 24 이상이 필요합니다. 프로젝트 경로에서 `scripts/install.cmd`로 의존성을 설치하고 `scripts/check.cmd`로 빌드와 단위 시험을 실행합니다. 실행 파일은 `scripts/serve.cmd`이며 화면은 [Naru 열기](http://127.0.0.1:49170)에서 사용할 수 있습니다.

장기 작업을 화면 없이 시작하려면 PowerShell에서 다음과 같이 실행합니다. 설치와 빌드에도 같은 방식으로 해당 cmd 파일을 지정합니다.

```powershell
$naruStartup = New-CimInstance -CimClass (Get-CimClass Win32_ProcessStartup) -Property @{ ShowWindow = [uint16]0 } -ClientOnly
Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{
  CommandLine = 'cmd /d /c D:\PROJECTS\Naru\scripts\serve.cmd'
  CurrentDirectory = 'D:\PROJECTS\Naru'
  ProcessStartupInformation = $naruStartup
}
```

로그와 종료코드는 `.local`에 저장됩니다. process manager에 서비스를 등록한 환경에서는 process manager로 시작하고 종료합니다. 서버는 loopback에만 바인딩합니다.

처음 실행하면 화면에서 런타임을 설치하고 시작합니다. 공식 WSL rootfs를 다운로드하고 SHA256을 검증한 뒤 `naru` 배포판을 생성합니다. 인터넷 연결과 디스크 공간이 필요합니다. 기존 External Engine 배포판과 데이터는 별도로 유지합니다.

## 엔진 연결

설정의 **연결할 엔진**에서 Naru 독립 엔진 또는 External Engine 공유를 선택합니다. 기존 데이터를 옮길 때는 먼저 백업하고 [이관 회고](docs/reviews/261016-external-data-migration.md)의 절차와 검증 항목을 참고합니다.

독립 모드의 Windows 연결은 Naru 서버가 여는 named pipe입니다. Docker 기본 context `naru`는 `naru_engine`을 쓰고, External Engine이 실행 중이 아니면 기본 `docker_engine` pipe도 같은 엔진으로 연결하여 context를 읽지 않는 Docker SDK와 도구도 그대로 동작합니다. 설정의 **Naru 서버 시작 시 엔진도 시작**(기본 켬)으로 서버가 시작될 때 엔진과 재시작 정책이 있는 컨테이너가 함께 올라옵니다. process manager를 사용하는 환경에서는 패드의 자동 시작을 설정할 수 있습니다.

독립 모드의 pipe 연결은 External Engine처럼 컨테이너와 볼륨 생성 요청의 Windows 경로(`D:\work\app`)를 `/mnt/d/work/app`으로 바꿔 전달합니다. 그래서 Windows 터미널의 `docker run -v D:\...`와 상대 bind가 있는 `docker compose up`이 그대로 동작합니다. 다만 표준 입력을 넘긴 뒤 출력을 기다리는 `docker exec -i ... < file`과 `docker run -i`는 Windows named pipe에서 끝나지 않는 문제가 남아 있습니다. 당분간은 `docker exec ... sh -c "..."`나 WSL 안의 docker를 사용합니다.

dockerd는 `/etc/naru/dockerd.json`의 containerd snapshotter와 `min-api-version 1.41`을 사용하여 External Engine과 같은 이미지 저장소와 API 범위를 유지합니다. 컨테이너가 공개한 포트는 WSL localhost 전달로 Windows의 `127.0.0.1`에서 접속합니다. 모든 WSL 배포판이 같은 네트워크를 공유하므로 External Engine 엔진과 Naru 엔진을 동시에 실행하지 않습니다.

## Tailscale 원격 접속

기본값은 이 PC의 `127.0.0.1`에서만 접속을 허용합니다. tailnet에서 쓰려면 `tailscale serve --bg --https=<포트> http://127.0.0.1:49170`로 연결하고 `%LOCALAPPDATA%\Naru\remote.json`에 serve 주소와 허용할 tailnet 로그인을 적은 뒤 서버를 다시 시작합니다.

```json
{ "host": "<기기>.<tailnet>.ts.net:<포트>", "users": ["<tailnet 로그인>"] }
```

원격 요청은 loopback으로 들어온 serve 요청이면서 Host, Origin과 serve가 검증해 넣는 `Tailscale-User-Login`이 모두 일치할 때만 허용합니다. 확장 화면은 `*.localhost` 격리 출처를 쓰므로 이 PC에서만 열립니다.

## 사용

기본 표시 언어는 영어입니다. **Settings > Display > Language**에서 **한국어** 또는 **English**를 선택하면 즉시 적용되며 이 브라우저에 저장됩니다. 서버의 설정 저장 버튼과 별도로 적용됩니다.

- **커맨드 팔레트 (`Ctrl+K`)**: 화면 어디서나 키보드 단축키로 Naru의 메뉴 이동, 컨테이너 검색, 주요 관리 작업을 즉시 실행할 수 있습니다.
- **실시간 실행 상태 위젯**: 상단바에 현재 실행 중인 컨테이너 대수를 항상 표시하며, 클릭 시 즉시 컨테이너 목록으로 이동합니다.

Naru의 사이드바에는 11개 메뉴가 있습니다. 실행할 프로그램을 준비하는 **이미지**, 실제 프로그램을 제어하는 **컨테이너**, 데이터와 통신을 담당하는 **볼륨과 네트워크**를 중심으로 이해하면 쉬워요. Compose 프로젝트 관리는 컨테이너 메뉴에 통합되어 있습니다.

| 메뉴 | 역할 | 주로 사용하는 상황 |
| --- | --- | --- |
| 컨테이너 | 실행 중인 프로그램과 Compose 프로젝트 관리 | 앱 실행, 정지, 로그 확인과 재시작 |
| 이미지 | 실행 패키지와 버전 관리 | 이미지 다운로드, 빌드와 배포 준비 |
| Kubernetes | 로컬 Kubernetes와 배포 리소스 관리 | Kubernetes YAML과 배포 상태 시험 |
| 포트 전달 | Kubernetes 내부 리소스를 로컬 포트에 연결 | 브라우저나 개발 도구로 내부 서비스 접속 |
| 볼륨 | 컨테이너와 분리된 지속 저장 공간 관리 | DB와 업로드 파일 보존 |
| 네트워크 | 컨테이너 사이의 통신 구성 관리 | 앱과 DB 연결, 프로젝트별 네트워크 확인 |
| 스냅샷 | Naru 독립 실행 환경 저장과 복원 | 큰 변경 전 백업과 이전 상태 복구 |
| 확장 | 추가 개발 도구 설치와 실행 | 기본 기능에 필요한 도구 추가 |
| 작업 기록 | 요청한 작업의 진행과 결과 확인 | 다운로드, 빌드와 설치 결과 추적 |
| 진단 | 기반 환경의 상태와 로그 확인 | 엔진과 Kubernetes 실행 문제 조사 |
| 설정 | 실행 방식과 연결 도구 설정 | 엔진 선택, 자동 시작과 CLI 준비 |

**연결 모드에 따른 범위:** Naru 독립 엔진에서는 위 기능을 Naru에서 관리합니다. External Engine 공유 모드에서는 컨테이너, 이미지, 볼륨, 네트워크와 Compose를 Naru에서 관리하며, Kubernetes, 포트 전달, 스냅샷과 확장 화면은 External Engine에서 관리하도록 안내해요. 공유 모드의 실행 환경 설정도 External Engine에서 관리합니다.

### 1. 컨테이너

컨테이너는 웹 서버, 데이터베이스, Redis 같은 프로그램이 실제로 실행되는 단위예요. 이 메뉴에서는 실행 상태, 사용 이미지와 공개된 포트를 확인하고, 컨테이너를 생성하거나 시작, 정지, 복제, 삭제합니다. 전체, 실행 중, 종료됨으로 나누어 조회하고 이름으로 검색할 수 있습니다.

- **빠른 시작 템플릿과 컨테이너 복제**: Nginx, Redis, PostgreSQL, MySQL, Node.js, Ubuntu 템플릿으로 원클릭 생성할 수 있습니다. 기존 컨테이너의 설정(이미지, 환경 변수, 볼륨, 명령)을 복사하고 포트 충돌을 방지(+1)해 복제하는 기능도 지원해요.
- **Docker Run CLI 양방향 변환과 환경 변수 프리셋**: 터미널의 `docker run` 명령어를 붙여넣어 폼을 자동 채우고, 폼에 입력한 내용을 실시간 `docker run` 명령어로 역생성해 복사할 수 있습니다. 추천 프리셋(Node.js, PostgreSQL, Redis 등)과 커스텀 프리셋 저장도 지원합니다.
- **`*.naru.localhost` 가상 도메인 자동 프록시**: 포트 번호를 외울 필요 없이 `http://<컨테이너이름>.naru.localhost:49170` 주소로 브라우저에서 바로 접속할 수 있습니다.
- **다중 선택 일괄 제어와 미사용 리소스 정리**: 여러 컨테이너를 한 번에 일괄 시작, 정지, 삭제할 수 있으며, 툴바의 미사용 리소스 정리(Prune) 버튼으로 가상 디스크 용량을 회수합니다.

상세 화면의 탭은 다음 역할을 담당합니다.

| 탭 | 역할과 사용 목적 |
| --- | --- |
| 로그 | 프로그램이 출력한 실행 기록과 오류를 확인해요. 실시간 검색 필터링, 최신 로그 자동 스크롤 추적과 원클릭 복사를 지원합니다. |
| 리소스 | CPU, 메모리, 네트워크 사용량을 확인합니다. CPU 80% 또는 메모리 85% 초과 시 리소스 과점 및 메모리 누수 경보와 원클릭 재시작을 제공해요. |
| 파일 | 컨테이너 내부 파일 트리를 브라우저에서 직접 탐색하고, 설정이나 로그 파일을 열람 및 수정하거나 로컬 파일을 업로드/다운로드합니다. |
| 터미널 | 컨테이너 내부에서 대화형으로 명령을 실행해요. Moby와 containerd 모두 실제 PTY를 사용합니다. |
| 명령 실행 | 문자열 JSON 배열로 지정한 명령을 한 번 실행하고 결과를 확인합니다. 특정 점검 명령을 실행할 때 사용해요. |
| 구성 | 엔진이 가진 상세 구성을 확인해요. 환경 변수, 마운트와 네트워크 등 실제 적용값을 조사합니다. |

#### Compose 프로젝트

웹앱 하나가 웹 서버, DB와 Redis 등 여러 컨테이너로 구성될 수 있어요. Compose 프로젝트는 이들을 하나의 애플리케이션 단위로 묶어 관리합니다. 컨테이너 화면은 Compose 라벨로 프로젝트를 구분하며, 프로젝트별로 접고 펼칠 수 있어요.

프로젝트 관리 모달에서는 **아키텍처 토폴로지 맵**을 통해 소속 서비스들의 기동 상태, 이미지, 연결 네트워크, 포트 매핑과 가상 도메인 링크를 카드 형태로 시각화합니다. 프로젝트 단위로 시작, 정지, 재시작과 통합 로그 확인을 수행하며, 원본 Compose 파일이 있으면 다음 작업도 사용할 수 있어요.

| 작업 | 역할 |
| --- | --- |
| `up` | Compose 정의에 따라 컨테이너를 생성하거나 변경 사항을 반영해 실행합니다. |
| `down` | 프로젝트의 컨테이너와 네트워크를 제거해요. 이름 있는 볼륨은 보존합니다. |
| `pull` | 프로젝트에서 사용하는 이미지를 가져옵니다. |
| `build` | Compose에 정의한 이미지를 빌드해요. |

프로젝트 목록은 `%LOCALAPPDATA%\Naru\projects.json`에도 기록하므로 `down` 이후에도 다시 `up`할 수 있습니다. Compose 파일이 없는 프로젝트는 컨테이너 시작, 정지와 재시작을 제공합니다. 새 프로젝트는 `%LOCALAPPDATA%\Naru\compose\<이름>\compose.yaml`에 저장하고 화면에서 편집해요.

**필요한 이유:** 여러 서비스를 함께 실행하고 종료하며, 프로젝트의 실행 구성을 재사용하기 위해 필요합니다.

### 2. 이미지

이미지는 컨테이너를 만드는 실행 패키지예요. 프로그램과 실행에 필요한 파일, 기본 설정 등을 담으며, 같은 이미지로 설정이 다른 컨테이너를 여러 개 만들 수 있습니다.

이미지 메뉴에서는 레지스트리에서 가져오기(`pull`), Dockerfile과 Windows 소스 폴더를 이용한 빌드, 컨테이너 실행, 태그 추가, 레지스트리로 보내기(`push`), TAR 내보내기와 불러오기, 삭제, 레이어 분석과 취약점 분석을 수행해요.

- **이미지 레이어 용량 분석기**: 각 이미지 행의 레이어 아이콘을 클릭하면 Dockerfile 빌드 단계별 레이어 크기, 실행 명령어와 용량 점유율을 시각적 막대 그래프로 분석할 수 있습니다. 50MB 이상의 대용량 레이어를 빠르게 식별하여 이미지 경량화를 돕습니다.

**필요한 이유:** 실행할 프로그램의 종류와 버전을 준비하고 관리하기 위해 필요합니다. 직접 개발한 앱을 `my-app:1.0`으로 빌드하고, 새 버전을 `my-app:1.1`로 구분하거나 다른 PC로 실행 패키지를 옮길 때 사용해요. TAR 파일은 실행 패키지를 옮기는 용도이며, 실행 중인 DB 데이터는 볼륨 등 해당 데이터의 저장 위치를 별도로 백업합니다.

이미지 취약점 검사는 Trivy를 사용해요. 현재 실제 취약점 DB 다운로드 시험은 남아 있습니다.

### 3. Kubernetes

Kubernetes 메뉴는 로컬 k3s 실행 환경과 그 안에 배포한 리소스를 관리해요. k3s 설치와 시작, 종료, 종류와 네임스페이스별 조회, 다중 YAML 적용, 리소스 구성 확인과 삭제, Pod 로그 확인과 kubeconfig 다운로드를 지원합니다. Windows API 연결은 Naru의 로컬 TCP bridge로 전달해요.

현재 조회할 수 있는 리소스는 다음과 같습니다.

| 리소스 | 역할 |
| --- | --- |
| 파드, Pod | 프로그램이 실행되는 기본 단위예요. |
| 디플로이먼트, Deployment | 원하는 수의 파드를 유지하고 배포 상태를 관리합니다. |
| 서비스, Service | 파드에 접근할 수 있는 일정한 접점을 제공해요. |
| 노드, Node | 파드가 실행되는 머신의 상태를 나타냅니다. |
| 네임스페이스, Namespace | 프로젝트나 용도별로 리소스를 구분하는 공간이에요. |
| ConfigMap | 애플리케이션에 전달할 일반 설정을 보관합니다. |
| 볼륨 클레임, PVC | 애플리케이션이 사용할 지속 저장 공간을 요청해요. |
| 이벤트, Event | 배포와 실행 과정에서 발생한 상황을 확인합니다. |

**필요한 이유:** Kubernetes에 배포할 애플리케이션을 로컬에서도 같은 방식으로 시험하기 위해 필요해요. YAML의 설정, 파드 실행 상태와 서비스 연결을 개발 단계에서 확인합니다. Docker와 Compose 중심의 개발에서는 해당 기능을 사용하고, Kubernetes 배포를 개발하거나 학습할 때 이 메뉴를 활용하면 돼요.

### 4. 포트 전달

Kubernetes 내부 리소스의 포트를 Windows 로컬 포트로 연결하는 메뉴입니다. 예를 들어 `127.0.0.1:8080 → svc/my-web:80`으로 연결하면 브라우저에서 `http://127.0.0.1:8080`으로 해당 서비스에 접속할 수 있어요.

대상 Service, Pod 또는 Deployment와 네임스페이스, 로컬 포트와 대상 포트를 지정합니다. 전달 상태 확인, 전달 종료와 종료된 기록 삭제도 제공해요.

**필요한 이유:** 클러스터 내부 서비스에 개발 PC로 접속해 웹 화면, API와 DB 연결을 점검하기 위해 필요합니다. 이 메뉴는 Kubernetes 포트 전달을 담당하며, Docker 컨테이너의 `8080:80` 같은 포트 공개는 컨테이너 생성 시 지정해요.

### 5. 볼륨

볼륨은 컨테이너의 수명과 분리해 데이터를 보관하는 저장 공간입니다. 메뉴에서 이름, 드라이버와 마운트 경로를 확인하고 생성, 상세 구성 조회와 삭제를 수행해요.

- **볼륨 내부 파일 탐색기**: 볼륨 목록의 폴더 아이콘을 클릭하면 컨테이너를 실행하지 않아도 볼륨 내부의 디렉터리와 파일을 브라우저에서 직접 탐색하고, 텍스트 파일을 수정하거나 로컬 파일을 업로드할 수 있습니다.
- **원클릭 백업 및 복원**: 볼륨 전체 데이터를 `.tar.gz` 스트림으로 압축 다운로드하여 백업하고, 기존 아카이브 파일을 업로드하여 원클릭으로 복원할 수 있습니다.

**필요한 이유:** 컨테이너를 교체해도 DB 파일이나 업로드 파일처럼 유지할 데이터를 보존하기 위해 필요합니다. 예를 들어 PostgreSQL 데이터를 볼륨에 저장하면 컨테이너를 다시 만들 때 해당 볼륨을 연결하는 구성을 사용할 수 있어요. 볼륨 삭제는 저장된 데이터도 함께 삭제하므로 화면에서 삭제 전에 확인합니다.

### 6. 네트워크

네트워크 메뉴는 컨테이너 사이의 통신 구성을 관리해요. 네트워크를 생성하고 이름, 드라이버와 범위를 확인하며, 상세 구성 조회와 삭제를 수행합니다.

- **연결 토폴로지 확인**: 네트워크 행이나 진단 아이콘을 클릭하면 네트워크에 연결된 컨테이너들의 IP와 MAC 주소를 한눈에 확인할 수 있습니다.
- **컨테이너 간 핑(Ping) 및 포트 점검**: 출발지 컨테이너를 선택하고 목적지(컨테이너명, IP, 외부 호스트)와 포트를 지정하여 실시간 핑과 TCP 포트 통신 성공 여부를 원클릭으로 진단합니다.

**필요한 이유:** 앱과 DB를 연결하고 프로젝트마다 연결 범위를 구분하기 위해 필요해요. 사용자 정의 Docker 네트워크에서는 같은 네트워크의 컨테이너가 이름으로 상대를 찾는 구성을 사용할 수 있습니다. 예를 들어 앱이 `db:5432`로 접속할 때 두 컨테이너의 네트워크 연결을 확인하는 데 활용해요.

Compose는 프로젝트 네트워크를 보통 자동으로 구성합니다. 연결 문제를 조사하거나 여러 프로젝트가 사용할 공용 네트워크를 준비할 때 이 메뉴가 유용해요.

### 7. 스냅샷

스냅샷은 Naru 독립 WSL 배포판을 정지해 내보내고, 저장한 시점으로 복원하는 기능입니다. 실행 중에 생성하면 백업 후 엔진을 다시 시작해요. 화면에서 이름, 생성 시각과 크기를 확인하고 생성, 복원과 삭제를 수행합니다.

**필요한 이유:** 엔진이나 개발 환경을 크게 변경하기 전에 복구 기준점을 확보하기 위해 필요해요. 문제가 생겼을 때 저장한 환경으로 돌아가는 수단입니다.

복원은 현재 Naru 데이터를 스냅샷의 상태로 교체하며, 교체 직전에 현재 배포판의 백업도 별도로 생성해요. 복원과 삭제는 화면의 확인 절차를 거칩니다. Windows 폴더를 연결한 bind mount의 원본 데이터는 배포판 밖에 있으므로 별도로 백업해요.

### 8. 확장

확장 메뉴는 OCI 이미지로 배포되는 추가 개발 도구를 설치하고 관리합니다. 설치된 확장을 확인하고, UI가 있는 확장을 열거나 제거할 수 있어요. 패키지에 따라 UI, VM 서비스와 Windows 실행파일을 제공합니다.

**필요한 이유:** 자주 사용하는 추가 도구를 Naru 작업 환경에 통합하기 위해 필요해요. 필요한 도구가 생겼을 때 사용하는 선택 기능입니다.

UI는 확장별 localhost origin으로 격리됩니다. 확장은 엔진, VM과 선언된 host 실행 권한을 가지므로 신뢰하는 이미지에 한해 설치하며, 설치 시 `TRUST` 확인을 받아요. 확장 화면은 이 PC에서 열 수 있습니다. 전체 Docker Desktop SDK 호환은 추가 검증 대상입니다.

### 9. 작업 기록

작업 기록은 Naru에 요청한 작업의 진행 상태와 결과를 보여줘요. 작업 종류, 상태, 시작 시각과 결과를 확인하고, 항목을 눌러 상세 진행 내용과 로그를 열 수 있습니다. 작업 종류와 상태별 필터도 제공해요.

**필요한 이유:** 이미지 다운로드, 빌드, 런타임 설치와 스냅샷 생성처럼 시간이 걸리는 작업의 접수, 진행과 완료 여부를 추적하기 위해 필요합니다. 예를 들어 빌드가 실패하면 해당 작업의 출력에서 실패 원인을 살펴볼 수 있어요. 상단의 진행 중 작업 표시로도 상세 내용을 열 수 있습니다.

### 10. 진단

진단은 Naru를 구동하는 기반 환경의 상태와 로그를 확인하는 화면이에요. WSL 배포판 목록, 제어 서버 메모리 사용량, Node.js 버전과 데이터 경로, 엔진과 Kubernetes 및 빌드 엔진 로그를 제공합니다.

**필요한 이유:** 엔진이 시작되지 않거나 Kubernetes 실행에 문제가 생겼을 때 기반 환경의 정보를 확인하기 위해 필요해요. 문제 유형에 따라 다음 화면을 활용합니다.

| 확인할 상황 | 사용할 화면 |
| --- | --- |
| 앱이 오류를 출력해요 | 컨테이너 상세의 로그 |
| 빌드나 설치 요청이 실패했어요 | 작업 기록의 상세 로그 |
| 엔진이나 Kubernetes 자체의 시작에 문제가 있어요 | 진단 |

진단은 현재 상태와 로그를 제공하는 조사 화면입니다.

### 11. 설정

설정은 Naru의 실행 방식과 연결 도구를 정하는 메뉴예요. 다섯 개 탭으로 구성합니다.

| 탭 | 설정 내용 | 필요한 이유 |
| --- | --- | --- |
| 엔진 | 연결 모드, Moby와 containerd 선택, containerd 네임스페이스, 런타임 설치와 시작 및 종료, 서버 시작 시 엔진 자동 시작 | 사용할 실행 기반을 정하고 관리해요. |
| Kubernetes | 엔진 시작 시 함께 시작할지, k3s 버전, API 포트와 Traefik Ingress 사용 | 개발할 Kubernetes 환경의 동작 조건을 맞춥니다. |
| 프록시 | `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` | 프록시가 필요한 환경에서 외부 통신 경로를 설정해요. |
| 화면 | 자동 갱신 간격 | 상태 확인 주기와 반복 조회 빈도를 조절합니다. |
| CLI와 레지스트리 | Windows CLI 설치, 레지스트리 로그인과 로그아웃 | 터미널에서도 같은 엔진을 사용하고 인증이 필요한 이미지를 주고받아요. |

**필요한 이유:** 화면과 터미널이 같은 실행 환경을 사용하도록 연결하고, 네트워크와 개발 방식에 맞춰 실행 조건을 조정하기 위해 필요합니다. 엔진, Kubernetes와 프록시의 주요 설정은 엔진을 정상 종료한 뒤 변경해요. 서버 시작 시 엔진 자동 시작과 화면 설정은 실행 중에도 저장할 수 있습니다.

Windows CLI 설치는 공식 Docker, Compose, Buildx, kubectl, Helm과 credential helper를 검증해 설치해요. 기존 Docker CLI의 기본 context를 선택한 모드에 맞춰 연결하며 `docker ps`, `docker compose`를 그대로 사용합니다. 컨테이너 CLI는 표준 Docker 도구를 사용해요. Docker 자격 증명 설정은 보존하며 Naru가 설치한 Compose와 Buildx 검색 경로를 추가합니다. Docker가 PATH에 없는 환경에서는 `%LOCALAPPDATA%\Naru\bin\docker.exe`를 사용해요. kubeconfig는 Naru 전용입니다.

레지스트리 로그인은 비공개 이미지 접근과 업로드에 필요한 인증을 관리해요. Docker 자격 증명 도우미를 통해 현재 Windows 사용자의 자격 증명 저장소에 보관합니다.

### 사용 흐름

Docker와 Compose 개발은 **설정에서 엔진 준비 → 이미지 가져오기 또는 빌드 → 컨테이너나 Compose 프로젝트 실행 → 로그와 리소스 확인** 순으로 진행하면 돼요. 데이터 보존은 볼륨, 컨테이너 사이의 연결 확인은 네트워크에서 처리합니다.

Kubernetes 개발은 **Kubernetes 시작 → YAML 적용 → 리소스 상태와 Pod 로그 확인 → 포트 전달로 접속 시험** 순으로 진행해요. 환경을 크게 변경하기 전에는 스냅샷을 만들고, 작업의 진행과 결과는 작업 기록에서, 기반 환경의 문제는 진단에서 확인합니다.

## 데이터와 구조

기본 데이터 경로는 `%LOCALAPPDATA%\Naru`입니다. `NARU_DATA_DIR`로 변경할 수 있습니다. WSL 배포판 이름은 `naru`로 고정되어 있어 데이터 경로를 바꿔도 별도의 배포판 인스턴스가 생기지 않습니다. 엔진 데이터는 배포판의 `/var/lib/naru`에, 설정과 작업 기록, 확장, 다운로드 캐시와 스냅샷은 Windows 데이터 경로에 저장합니다.

`server/`는 로컬 API, WSL 런타임, 작업 프로세스와 연결 계층입니다. `src/`는 React 화면과 공용 컴포넌트입니다. 화면 스타일은 Tailwind CSS v4 유틸리티로 작성합니다. 색상, 글꼴과 브레이크포인트는 `src/tailwind.css`의 `@theme`에, 여러 화면이 함께 쓰는 클래스 묶음은 `src/tw.js`에 있습니다. 간격 단위는 4px입니다. AG Grid 내부 요소의 테마만 `src/components/DataGrid/data-grid.css`에 둡니다. 큰 표와 터미널은 필요할 때 로드합니다. Docker 연결 재사용과 짧은 목록 캐시로 반복 WSL 프로세스 생성을 줄입니다. 주요 변경 작업은 별도 WMI worker가 실행하며 기록을 저장합니다. 종료된 worker의 작업 상태와 잠금은 다음 조회 또는 제출 때 복구합니다.

## 검증과 대체 판정

통합 시험을 실행하기 전에 로컬 `evidence/` 폴더를 생성합니다. 시험 결과는 `evidence/*.json`에 기록하며 공개 저장소에는 포함하지 않습니다. 시험 코드는 `tests/`에 있습니다. 통합 시험은 Naru 배포판의 엔진과 시험용 컨테이너를 변경하며, advanced 시험에는 스냅샷 복원이 포함됩니다. 사용할 데이터가 있는 환경에서는 시험 내용을 확인하고 별도 백업 후 실행합니다.

현재 Windows의 주요 개발 흐름은 실제 실행 증거를 확보했습니다. **완전 대체 판정은 계속 검증 중입니다.** 타 WSL 배포판 통합, 기업 CA와 VPN, locked 정책과 allowlist, CLI 자동화 호환, 업그레이드와 다운그레이드 복구, macOS와 Linux 등은 구현 또는 검증이 남아 있습니다. 상세 범위는 [기능 감사](docs/specs/261015-parity-audit.md)와 [검증 회고](docs/reviews/261015-verification.md)를 참고합니다.
